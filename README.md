# 产品经理文档工作流

来源：微信公众号：松鼠的AI笔记。

本仓库提供一套面向产品经理的 AI 文档工作流。`CLAUDE.md` 是核心执行说明，它把需求沟通、需求拆解、需求文档生成、页面原型生成和后续变更同步整理成一套可恢复、可审查、可持续维护的流程。

## 核心原则

这套工作流的第一原则是：不得默认接受模糊不清的需求。

当需求存在歧义、矛盾、关键信息缺失、范围过大或技术不可行时，AI 必须先停下来追问，不能自行脑补，也不能用模棱两可的方式继续推进。它的目标不是快速产出一份看起来完整的文档，而是帮助产品经理把真实需求梳理清楚。

## 启动与状态恢复

每次开始工作时，AI 会优先检查项目根目录下的 `.pm_state.json` 状态文件。

- 如果状态文件存在，则读取当前阶段、需求文档、原型文件夹、定稿状态和上次中断点，并从中断点继续。
- 如果状态文件不存在，但已经有需求文档或原型交付物，则根据现有文件推断当前工作状态。
- 如果状态文件和交付物都不存在，则进入全新的需求启动流程，等待用户描述产品需求。

状态文件用于记录当前阶段、文档路径、原型路径、review 结果和功能拆解清单。每次到达关键检查点后都需要立即更新，保证长流程中断后仍然可以继续推进。

## 阶段一：需求拆解

用户开始描述产品需求后，AI 会进入需求拆解阶段，重点澄清以下内容：

- 产品目标与核心价值。
- 目标用户与使用场景。
- 功能列表。
- 功能边界，也就是做什么和不做什么。
- 非功能性需求，包括权限、性能、兼容性等。

在这个阶段，AI 必须主动指出描述模糊、关键信息缺失、逻辑冲突、范围过大和技术风险。只有这些问题被澄清后，才会输出功能拆解清单，并等待用户明确确认。

## 阶段二：生成需求文档

用户确认功能拆解后，AI 会读取 `templates/需求说明文档模板.html`，严格按照模板结构生成需求说明文档。

文档生成后会进入 review 流程，重点检查：

- 逻辑完整性：流程是否闭环，是否遗漏场景或异常处理。
- 表达清晰度：是否存在歧义，开发人员能否直接实现。
- 技术可行性：是否存在实现障碍或高风险点。
- 内部一致性：文档各部分是否互相矛盾。

如果 review 发现阻断或重要问题，需要先修正文档并重新 review。只有 review 通过或建议项被处理后，才等待用户确认文档定稿。

## 阶段三：生成页面原型

需求文档定稿后，AI 会询问是否需要生成 HTML 页面原型。

如果需要生成原型，流程会先根据需求文档梳理页面清单，并等待用户确认。随后 AI 会读取 `templates/原型备注模板.html`，为主要功能模块生成 HTML 原型页面。

原型要求包括：

- 使用真实 UI 组件结构，如表单、按钮、表格、弹窗等。
- 呈现必要的交互状态，如空状态、填写状态、错误状态和加载状态。
- 页面间导航链接必须可点击。
- 在页面中嵌入交互说明与逻辑备注。

原型生成后也会运行一致性 review，检查页面覆盖、交互逻辑、字段按钮状态和备注是否与需求文档对齐。

## 阶段四：变更同步

当需求文档和页面原型都已定稿后，只要用户修改其中任意一方，就会进入变更同步阶段。

- 修改需求文档后，需要询问是否同步修改页面原型。
- 修改页面原型后，需要询问是否同步修改需求文档。
- 任意一方发生变更时，需要根据变更范围更新版本号。
- 文档文件名、原型文件夹名和 `.pm_state.json` 中的路径需要保持一致。

这一步的作用是避免文档和原型逐渐分叉，保证产品、设计、前端、后端和测试始终围绕同一套交付物协作。

## 需求文档模板亮点

`templates/需求说明文档模板.html` 内置了可编辑能力：

- 双击文档正文区域，可以进入编辑状态。
- 编辑后页面右上角会出现保存工具条。
- 保存时选择原文件并覆盖，即可更新当前需求文档。

因此，需求文档既可以作为可阅读的 HTML 文档，也可以在浏览器中直接进行轻量编辑，适合评审现场修改和快速更新。
